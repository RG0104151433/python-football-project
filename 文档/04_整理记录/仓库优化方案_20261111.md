# 仓库优化方案：先看成果，再查证据

本方案根据2026年11月11日的工作区检查制定。目标是让第一次进入仓库的人迅速找到论文、展示、研究结论和运行方法，同时保留必要的研究过程。

**本轮已做：** 继续缩短现有英文讲稿并同步三份取用副本；优化展示、论文和研究入口的当前说明，将旧状态折叠保留；首页加入本方案链接。

**2026-11-11执行更新（R20261111-02）：** 用户授权按本方案整理后，已完成旧展示/Archify/来源记录、论文早期规划与初稿清单的分组归档，并清理可再生缓存。执行清单见[仓库优化执行记录](仓库优化执行记录_20261111.json)。正式论文、V4/V5 HTML、科研数据及已提交ZIP未改；构建/研究脚本目录重排和大档案分发仍按后续事项处理。下文保留原方案的分步说明，是否已实施以本段及执行记录为准。

## 1. 目前为什么显得乱

- 展示目录直接可见51个条目，论文目录41个条目。正式成品、生成工具、旧稿和验收文件混在一起，新读者容易选错。
- 几个README将每次更新依次放在前面，出现多条互相冲突的“当前”状态。例如旧的10页讲义、V4/V5试验说明、论文尚未完成的记录仍容易被看到。入口应只解释现在怎么用；历史展开后再读。
- 运行脚本目录有128个直接条目。已有脚本导航，因此首先改善导航和正式入口标识，不急着重新移动全部脚本。
- 按`git ls-files`列出的、目前仍存在的文件统计，`outputs/`约2,507.65 MiB，`data/`约1,667.52 MiB；二者约4.08 GiB。展示约48.85 MiB，论文约3.45 MiB。这里统计的是Git跟踪的工作区文件大小，不是`.git`历史大小，也不包括全部本机缓存。减少几个说明文档不能解决大仓库问题。

## 2. 重要内容放在哪里

根目录不再复制论文、展示和压缩包，只保留清楚的导航。首次访问按以下顺序阅读：

1. `README.md`：一句话研究目的、少量主要结论、论文/展示/讲稿/快速检查四个入口。
2. `paper/final_paper.pdf`：唯一明确标作正式论文的入口；可编辑源为`paper/language_revision_20261107/main.tex`。根下旧`paper/main.tex`不能被说明成当前正式源。
3. `presentation/index.html`与`presentation/PRESENTATION_SCRIPT_EN.md`：当前V5和唯一维护的主讲稿；`repository_architecture.html`与结果模板一起保留。
4. `研究/README.md`：按研究逻辑阅读各问的结论，具体采用版本查`研究/pipeline_state.json`。
5. `文档/02_环境配置/克隆仓库后的快速上手.md`、`scripts/README.md`、`src/README.md`：供复现和代码阅读。
6. 研究日志与材料索引：保留现有路径，用来追查理由和证据；不把整本日志复制到每个首页。

`交付材料/`继续按邮件、平台、课堂、清单、历史五种用途存放。它是本机交付副本区，已提交附件保持原样，不作为另一套科研源目录。

## 3. 入口文档怎样优化

每个README开头只回答四件事：这是什么、现在看哪个、怎么用、还有什么没完成。版本沿革放在末尾的折叠区，不继续向前堆叠长摘要。

- 展示入口：只突出V5、短讲稿、赛果接入、三人彩排；旧10页PDF明确标作历史，不能当新版备用讲义。
- 论文入口：突出正式PDF、当前TeX源、证据索引和编译方式。旧页数、旧工具状态与旧写作计划留作历史。
- 研究入口：保持清洗/身份确认→第一至第九问的逻辑顺序，区分实算、条件验证、封存预测和文字展望。
- 材料索引：当前采用文件优先，历史对照另列；只引用已有文件，避免生成第二份相同成果。
- 根目录README维持简短中文导航；课程论文、幻灯内容和朗读部分继续使用英文。

## 4. 不常用的内容怎样集中存放

以下为原先拟议的位置。其中旧展示、Archify、来源记录、论文规划和初稿清单现已迁入对应archive子目录；checks/tools等脚本集中方案仍未实施。

### 展示目录

- 直接保留：当前HTML、结构图、讲稿、赛果清单与模板、README、来源入口、当前版本清单。
- `versions/`继续保留V3/V4/V5；V4冻结内容不变，V5讲稿副本随主稿同步，不在版本目录中独立修改。
- 旧`handout.pdf`、`figure_comparison.html`、`preview.png`可集中到拟建的`presentation/archive/initial_10_screen/`，并注明“不对应当前14页”。移动前检查HTML的Sources链接和构建器引用。
- 旧Archify图与凭证应成组移到拟建的`presentation/archive/archify_legacy/`，不能只留一张无来源的图。
- 验证脚本、摘要JSON和构建源可以分别集中到拟建的`presentation/checks/`、`presentation/tools/`。但当前构建入口、脚本导入及清单存在路径/源码指纹绑定，因此这一项放在展示结束后实施。当前先通过README区分即可。
- `assets/`保留实际使用的图片、数据、来源、许可；旧候选图片要先核对构建及历史引用，不能按“当前没显示”直接删。

### 论文目录

- 正式PDF、当前可编辑源、所用图、文献、证据清单放在清楚入口下；不在根目录另复制一份论文。
- 早期结构规划、初稿审查、修订比较可集中到`paper/archive/`的对应阶段；旧源必须连同所依赖的分章、图、文献保存，不能只挪走一个`main.tex`使其无法恢复。
- `paper/main.pdf`等重复输出，只有在核对所有使用方后才考虑取消生成。当前正式提交和清单有引用，暂保留。
- `paper/build/`是可重新生成的本机编译目录，可在保留最终PDF后清理；历史渲染检查需要保留的摘要不随缓存一起删。

### 科研与协作目录

- `研究/`继续按问题存放，不为减少文件数把九问混成一个目录。
- 旧方案放已有`文档/03_选题存档/`，整理记录放已有`文档/04_整理记录/`；长期日志留原处。历史日志只追加更正，不搬动或改写使旧决定看起来已预知结果。
- `outputs/review_layer1/`至`review_layer3/`是独立审查依据，可降低导航优先级；不当作一次性测试垃圾删除。
- `scripts/`先保留现有路径，在导航中区分正式运行、审计、历史试验；大规模重排以后再做，以免破坏已记录命令。

## 5. 哪些可以考虑删除

优先清理可自动重建、没有独立证据价值的本机文件：

- `__pycache__/`、`.pytest_cache/`、`outputs/test_tmp/`。
- `presentation/_build/`中的临时截图、虚构比分导出、下载或工具缓存；保留需要引用的验证摘要和素材来源。
- `paper/build/`中的中间编译文件与临时渲染图；先确认正式PDF及必要存档已在其他位置。
- 重新出现的重复ZIP、已核验解压目录、失效的临时下载。只留需要实际发送或恢复的一份。

`.mimosa/`、`.workbuddy/`目前是本机工具状态，不属于研究成果，可忽略或在相应工具退出后清理；若存在仍需使用的个人记忆，先自行保留。`.venv/`不是无用文件，删除后要重建环境，不列入常规清理。`.idea/`已被忽略但仍有少量旧跟踪文件，可在后续整理时取消机器专属配置的跟踪；这不是主要体积来源。

**不直接删除：** 原始快照、修正记录、采用版输入/结果、失败实验的关键证据、参考文献和许可、V4冻结版、论文旧版恢复包、已提交附件。大模拟表或检查点只有完成依赖核对、确认重建方法及备份后才能另行决定，不能一律称为无用文件。

## 6. 建议的执行顺序与验收

1. **现在：先整理阅读入口。** 简化README和讲稿，历史折叠保留，给出唯一正式入口。本轮已完成上述入口调整，尚未移动文件。
2. **展示前：只清理可再生缓存。** 不移动构建脚本、当前HTML依赖和研究数据。核对当前V5、冻结V4、论文及已提交ZIP的指纹。
3. **展示后：集中旧资料。** 每次只移动一组，登记旧路径→新路径，修复所有链接、构建入口和清单；对冻结版本保留原清单和身份，不能改旧指纹冒称未变。展示执行离线打开、赛果导入和结构图返回检查；论文按改动情况检查编译。
4. **最后才讨论体积。** 若仍需轻量公开仓库，单独列出“代码与采用证据”发布范围和大档案备份。普通移动或删除工作区文件不会自动减少已有Git历史。是否使用外部存储/LFS、是否迁移历史另行决定，本方案不自动执行。

完成标准：读者能从首页直接找到正式论文、V5、短稿和快速检查；当前说明不再混用旧版本；历史可追溯；正式成品和数据版本不变；无断链、无遗漏来源。目录变少不等于整理完成，能找对和用对才是标准。
