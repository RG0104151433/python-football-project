# 数据准备全流程指南

版本：2026-10-20。适用于本仓库现有国际男子国家队数据。

本指南规定从现有原始数据登记、外部资料获取，到清洗、纠错、审计和冻结的完整流程。本文中的新增文件、模块和命令是实施目标，除“当前起点”外，不表示已经实现。本阶段不训练模型、不比较测试集预测表现。

## 1. 当前起点与完成标准

原始数据已经移动到 `data/raw/international_results/`，包括四个 CSV、README 和 LICENSE。主研究使用 results、shootouts、former_names；goalscorers 留作原始资料，暂不纳入主流程。已有环境、依赖锁文件和 config.json；清洗及采集代码尚未实现。

此前对这份本地数据的只读统计是：results 49,945 行，1872-11-30 至 2026-10-06；截至 2024-12-31 有 48,142 行；shootouts 700 行；former_names 36 行；goalscorers 47,914 行。这些数字用于核对输入，不能预先指定为最终清洗行数。

完成本阶段，需要同时具备：

- 原始文件有哈希、来源记录和明确版本身份，后续运行不会改写它们。
- 补充资料有具体链接、取得时间、提取过程和使用范围。
- 每一处纠错、排除、补充都有机器可读记录，可以撤销并重新生成。
- 清洗结果能追踪到原始行；不确定记录有明确处置。
- 输出样本说明、字段字典、审计报告、时间窗口统计和三类探索图。
- 断网可以从固定输入重新生成数据；第二次运行结果一致。

## 2. 先固定范围与目录

### 2.1 先写下规则，再处理数据

在 `文档/01_项目方案/数据口径与冻结协议.md` 中记录：

- 主任务为国际男子成年国家队比赛；不额外声称只包含 FIFA 成员。
- 主分析截止日为 2024-12-31，原始文件中之后的比赛保留但不进入主实验。
- 赛果按含加时、不含点球的比分定义；点球胜者单独存储。
- 主流程保留数据集的球队身份体系，跨源匹配使用显式映射。
- 场地先采用原始 neutral；只有证据足够且经过记录的案例才覆盖。
- 当缺乏可靠开球时间时，后续 Elo 按日取统一赛前状态、赛后批量更新。
- 当前 config 的时间段先作为候选协议：热身至 1979、训练至 2014、验证至 2019、测试至 2024。审查覆盖和样本量后确认，确认过程不查看测试预测指标。
- 所有清洗规则对整个数据集一致应用，不能为了让模型效果变好才修改规则。

## 3. 阶段 A：登记现有原始快照

### 你要做什么

1. 确认原始文件齐全，可正常读取，不在 Excel 中打开后覆盖保存。
2. 登记已有本地副本，不为获得一个“最新版本”而重新下载替换。
3. 记录上游仓库地址、文件来源、已知的取得方式与时间。未知内容明确写 unknown。
4. 之后新增上游版本时，使用独立批次目录，不能覆盖本次输入。

### 程序要做什么

`snapshot.py` 对每个文件计算：相对路径、字节数、SHA-256、CSV 行数、字段、实际日期范围、编码、许可信息，写入 manifest.json。不是比赛日期的字段不能套用比赛日期范围统计。

同时区分：`registered_at` 是现在登记的时间；`acquired_at` 是实际取得时间。不能把登记时间伪称下载时间。

上游 commit 若能通过文件内容核对确认则记录；否则留空，并以本地文件哈希标识版本。不能把查询时上游最新 commit 直接当作本地副本所属 commit。此前文档提到的 commit 也需要核验。

验收：哈希再次计算一致；manifest 能准确定位本地输入；离线检查通过。此时只算“本地快照已登记”，不夸大为“上游全部来源已查明”。

## 4. 阶段 B：先审计，再决定获取哪些补充资料

### 4.1 自动审计的内容

保留 CSV 原始文本取值，对解析失败单独记录，不让自动类型推断吞掉异常。

- 日期能否严格解析，是否存在未知日期、无效日期或未来日期。
- 比分是否为非负整数；空值、字母、小数、无穷值不能填成 0。
- neutral 是否属于显式允许的 TRUE/FALSE 值；未知值不能默认成 False。
- 队名、赛事、举办地是否为空；是否存在首尾空白、编码异常。
- 同队自赛、整行相同、同日同双方、主客顺序反转的候选冲突。
- 极端比分、同队同日多场、历史球队名称等需要解释的记录。
- shootouts 是否匹配主比赛，点球胜者是否为参赛方；比分目标是否仍正确。
- former_names 中日期区间、缺失边界、重叠和歧义。

审计程序输出 input_audit.json、duplicate_candidates.csv 和 review_cases.csv。大比分只是核验线索，不能仅凭阈值直接删除。

### 4.2 建立问题清单

每个问题登记：`case_id`、涉及的原始记录 ID、问题类型、发现规则、优先级、状态、处理人、证据 ID、决定和理由。

优先处理顺序：比分/日期冲突 → 中立场与球队身份问题 → 赛事归属 → 其他展示字段。

当前 Tahiti 与 New Caledonia 的 1974 年记录应单独建案。RSSSF 对该月列有多场比赛但日期不详，因此不能按日期与球队组合直接去重，也不能把不详日期补成某月第一天。

### 4.3 抽查正常记录

除异常记录外，建议固定随机种子抽查约 30—50 场，覆盖不同年代、地区、友谊赛/正式赛、中立/非中立，以及加时/点球案例。记录抽样规则与抽中 ID。

这用于发现审计规则漏掉的问题，不能把小样本一致率宣称为全库准确率。

验收：每类问题有数量、案例和明确下一步；形成有边界的补充需求，不开展无目标整站采集。

## 5. 阶段 C：获取补充数据与证据

### 5.1 纠错和补全的来源顺序

优先查具体赛事或足协官方报告；其次按问题类型查 RSSSF、National Football Teams、11v11。Wikipedia 主要用来寻找脚注和原始报告。EU-Football 仅在网页或存档确实可读时使用。

这不是机械的权威排序：官方比赛是否认定为 A 级，与本项目是否纳入该场比赛，仍需按既定范围判断。多个网站互相引用不等于多份独立证据。

### 5.2 第一版以人工定向提取为主

1. 从 case_id 出发，搜索具体日期、双方球队和赛事。
2. 打开单场或具体年份档案，确认比分是哪个球队视角，区分常规时间、加时和点球。
3. 在 sources.csv 登记来源身份、用途、访问方式和已知使用限制。
4. 在 evidence.csv 登记 evidence_id、case_id、具体 URL、页面标题、访问时间、页面版本或存档地址、待核验字段、原文取值、标准化取值、提取方式、提取人和备注。
5. 页面未提供某个字段就记缺失，不从页面排列位置推断主场，也不凭常识补日期。
6. 对关键修改请另一位组员复核；无人复核时如实记录，不能填一个虚构审核人。

允许保存的下载文件放 supplemental，记录文件哈希。人工转录的数据同时保存提取脚本或转录记录。网页内容不适合复制分发时，仅保存结构化核验结论、必要简短摘录和具体链接，不把整站内容打包进仓库。

### 5.3 确需程序下载时

- 优先使用明确提供的下载入口；本轮尚未确认这些站点提供可自由批量获取的官方 API。
- 先检查站点条款、robots 和访问条件，按允许方式取得资料，不绕过限制。
- 固定来源 URL、请求参数和批次；保存实际取得时间与哈希。
- 设置超时、有限重试、合理访问间隔和本地缓存。
- 检查状态码、文件类型、表头和实际字段；登录页或错误页不能当 CSV 保存。
- 离线复现只读取已保存且允许使用的输入，不重新请求网站。

### 5.4 比赛以外的辅助数据

队名映射优先完成。映射至少包含 source、source_team、canonical_team_id、canonical_name、有效时间边界、证据和备注。历史球队继承存在歧义时人工判断，不能用模糊匹配直接合并；也不能把队名映射与举办国家映射混为同一张表。

外部 Elo 和 FIFA 排名列为可选支线，不阻塞比赛数据冻结。若获取，保存来源、官方发布日期/评级日期、取得时间、球队原名、映射 ID、名次和分值。比较必须对齐日期和共同球队。不要用当前排名补历史排名；官网无法提供目标日资料时，记录缺失。

它们第一版只用于一致性分析，不进入主模型特征。后来若作为预测特征，必须另审信息可得时间，按赛前已发布的数据关联。

阵容、裁判、观众等暂不批量补齐。新增字段必须有具体用途，否则不增加清洗负担。

验收：每份新增资料都能追到具体来源与提取过程；未取得的资料有缺失说明，而非伪造完整性。

## 6. 阶段 D：把纠错变成可重放的修改记录

### 6.1 原始行使用稳定身份

导入时给每个文件保留文件 SHA-256，并按 CSV 解析后的数据记录序号建立 row_id（从 1 开始，不含表头）。不要使用可能冲突的日期+球队作为唯一 ID，也不要把记录序号误叫物理文本行号。

组合 `文件哈希 + row_id` 作为原始记录定位依据。排序后、筛选后不得重新编号。新增比赛使用独立命名空间，如 `supplement:<批次>:<序号>`，并保留证据 ID。

### 6.2 amendments.jsonl 采用追加式事件

每行一个 JSON 事件，至少记录：

- event_id、amendment_id、case_id、事件类型、时间和操作者。
- 输入快照哈希、目标 row_id、拟执行操作（修改字段、排除、增加记录）。
- 字段名、原值、新值、理由、evidence_ids。
- 状态（proposed / approved / rejected / revoked）、审核人及时间；未审核可为空。
- 撤销或替代时引用原 amendment_id，不能悄悄改掉历史事件。

执行程序先重放事件，计算当前有效决定，只应用已 approved 且未撤销的修改。应用前检查目标快照和原值完全匹配；不一致就停止报错，不能悄悄套到另一版数据。

批量规则（例如去首尾空格）在规则文件/代码中统一定义，保存规则版本及受影响数量，不必人工为每行审批；行级补丁用于具体事实修正。

### 6.3 证据不充分如何处理

- 不影响核心字段的未知信息：保留缺失，并记录状态。
- 日期、比分、球队身份不确定，无法可靠参与时间回测：进入隔离清单，保留原始记录和原因。
- 是否有主场优势不确定：不能直接改为中立；可以保留已确认的赛果供不使用场地的流程使用，并通过资格字段排除出需要场地信息的比较。
- 同日同双方：只作为候选问题，不自动删除。整行完全一致也应按明确的审核规则处置，不静默 drop_duplicates。

不同模型比较必须取共同合格样本；必要时对不确定案例另做敏感性分析。不要为了维持初始行数而强行保留，也不要为了简化处理而隐去排除数量。

验收：可以展示一个修改前后实例，撤销后能恢复；更换输入快照时旧补丁不会误用。

## 7. 阶段 E：运行确定性的清洗流程

推荐按以下顺序实施，每步保存输入/输出数量和原因：

1. 验证快照哈希，读取原始文本，建立稳定记录 ID。
2. 标准化允许的格式：首尾空格、日期格式、明确的布尔值；保留原始取值或可回查原始记录。
3. 校验关键字段，把解析失败或结构不合格记录列入隔离候选。
4. 应用已批准的事实修改；若修复了候选异常，重新进行字段校验。
5. 合并已批准的新增比赛；检查范围、身份、日期、比分及是否与既有比赛重合。
6. 应用显式队名映射，保留原始队名；未匹配项进入 unmatched_supplement.csv，不自动模糊合并。
7. 关联 shootouts 等辅助信息。先确认关联键唯一；主客反转时显式转换双方视角。不允许多对多关联意外扩大比赛行数。
8. 处理已裁定的重复/冲突和隔离项，记录可参与评级、预测、场地研究等资格。
9. 计算 home/draw/away、净胜球、is_neutral、时间段等派生字段。本场净胜球后续只能用于赛后更新，不能用于本场赛前预测。
10. 应用截止窗口，保留窗口外排除记录；不在本阶段删掉 1980 年前的热身历史。
11. 按日期、稳定记录 ID 确定排序，输出 matches_clean.csv 和完整行追踪。

主数据字段至少包括：match_id、原始文件身份、row_id、date、双方原名及规范 ID、比分、tournament、city、country、is_neutral、outcome、goal_difference、time_split、质量/资格标记。字段类型、空值政策和含义写入 `文档/01_项目方案/数据字典.md`。

row_lineage.csv 记录每条原始/新增记录的最终状态：纳入、窗口外、隔离、确认重复或其他排除，以及对应最终 ID、case_id 和 amendment_id。互斥的最终状态用于行数对账，允许另存多个问题原因。

## 8. 阶段 F：质量检查、样本审查和探索图

### 8.1 必须自动验证

- match_id 唯一；纳入记录日期可解析，比分为非负整数，球队有效且不自赛。
- is_neutral 不存在被静默转换的未知值；outcome 与比分一致。
- 主分析没有超过截止日的比赛，时间段没有重叠或遗漏。
- 补丁只作用于正确快照和预期原值；新增记录有证据。
- 辅助数据关联没有扩大主表行数，未匹配项可解释。
- 原始输入数 + 已批准新增数 = 最终纳入数 + 各互斥排除状态数。
- 每条输出能追到原始记录或新增证据；raw 文件哈希未变化。

关键测试用人工小样例覆盖：FALSE 解析、非法比分、加时/点球口径、同日不同比赛不误删、反向球队关联、补丁撤销及旧值不符时报错。不要只测试“文件存在”。

### 8.2 人工检查与三类探索图

输出热身/训练/验证/测试样本量、年代与赛事覆盖、场地构成、隔离和修改数量。最终数量以此次清洗结果为准。

生成三类图：逐年比赛量与赛事构成；非中立场主胜/平/客胜比例及净胜球分布；按年代、友谊赛/正式赛的主场表现。比例提供 Wilson 区间，每张图标清样本量、分母、时间范围和来源。

只能表述描述性关联，不据此宣称主场因果效应。最终测试集可以用于预先规定的覆盖和质量审计；不在此阶段尝试模型、比较测试预测效果或借结果挑选数据规则。

验收：validation_report.json 无未解释的硬性错误；剩余不确定问题、排除政策和样本变化均写入 clean_log.md。

## 9. 阶段 G：冻结与离线复现

实现统一入口后，目标命令可设为以下形式；这些命令目前不能直接运行：

```powershell
.\.venv\Scripts\python.exe -m src.snapshot --verify
.\.venv\Scripts\python.exe -m src.audit --config config.json
.\.venv\Scripts\python.exe -m src.clean --config config.json
.\.venv\Scripts\python.exe -m src.validate --config config.json
.\.venv\Scripts\python.exe -m src.plots --config config.json
```

最后可以再封装一个数据准备入口，但无需等整个 Elo 项目的 main.py 完成。

冻结时保存：

- 输入、证据、映射、补丁、配置的哈希。
- 清洗规则版本、依赖版本、实际执行所用的代码 commit；若有未提交改动，明确记录工作区不干净，不能只填旧 commit 冒充执行版本。
- 核心输出文件哈希、实际行数、日期范围、各时间段数量及排除原因。
- 已知限制和未解决问题；单独标明可选外部排名资料是否已完成。

上述内容写入 freeze_manifest.json。代码 commit、输入哈希和产物清单共同定位版本；不要求把包含自身哈希的文件再哈希到自身内部。

断网重新运行两次，对比 matches_clean.csv、row_lineage.csv 等核心产物的哈希。运行时间等天然变化字段保存在独立运行日志，不影响核心输出比较。另一位组员从同一输入和依赖复现一次，核对数量与哈希。

确认后提交代码、输入登记、可分发的必要数据、补丁与结果，并打数据版本标签。新证据到来时开启下一版，不覆盖已冻结版本的审计历史；如果改变主数据，后续 Elo 和特征必须从头重放。

## 10. 建议如何分批推进

以下是依赖顺序，不是工期承诺：

1. 第一批：写数据口径协议，登记现有快照，实现只读审计，形成问题清单。做到这里再决定具体要查哪些网页。
2. 第二批：定向获取证据，完成队名映射、疑点裁定和修改事件记录。可将数据核查与清洗程序实现分给不同组员。
3. 第三批：实现清洗、关联、资格标记及逐行追踪；先在小样例验证，再跑全量。
4. 第四批：质量检查、样本审查、三类图、字典与日志，冻结数据并跨电脑复现。
5. 支线：外部 Elo/FIFA 快照及排名映射。可在主数据冻结后推进，不阻塞基础 Elo 开发。

本阶段交付给下一阶段的是“可追溯的比赛数据 + 明确的数据口径 + 稳定复现入口”，不是只有一个整理后的 CSV。
